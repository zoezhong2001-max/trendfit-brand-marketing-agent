# v0.4.0 品牌资产数据合同

状态：设计稿。字段名用于约束下一步实现，可在编码评审时小幅调整。

## 1. 对象边界

| 对象 | 职责 | 独立版本 | 可变方式 |
| --- | --- | --- | --- |
| `BrandProfile` | 品牌定位、人群、目标和品牌级边界 | 是 | 新建版本 |
| `CatalogItem` | 可被营销选择的泛商品 | 是 | 新建版本 |
| `Variant` | 商品下可购买/预约/参与的具体变体 | 随 CatalogItem | 新建父对象版本 |
| `Availability` | 市场、渠道、区域与时间可用性 | 随 CatalogItem | 新建父对象版本 |
| `Claim` | 可使用或禁止使用的卖点表达 | 是 | 新建版本 |
| `EvidenceRef` | 字段事实的来源定位 | 否，内容寻址 | 追加新来源 |
| `BrandAssetSnapshot` | 一次评审实际读取的对象版本集合 | 不可变 | 只能创建新快照 |
| `AssetSelection` | 某 Topic 下的选品结论 | 随 Assessment | 新建 Assessment |

## 2. 枚举

```text
catalog_item.type = physical_product | menu_item | service | digital_product | offline_experience
lifecycle.status = draft | in_review | active | paused | retired
marketing_readiness = needs_review | eligible | blocked | expired
fact_status = explicit | inferred | hypothesis | unknown
review_status = unreviewed | confirmed | corrected | rejected
availability.status = available | unavailable | unknown
claim.policy = allowed | conditional | prohibited
asset_selection.decision = selected | needs_evidence | excluded
```

`fact_status` 表示信息性质，`review_status` 表示人的处理结果，两者不能合并。例如文件明确写出的事实仍可能尚未被人工确认。

## 6. BrandAssetSnapshot 示例

```json
{
  "id": "BAS-NAIXUE-0001",
  "brand_id": "BR-NAIXUE",
  "created_at": "2026-09-11T00:00:00+08:00",
  "brand_profile": {"id": "BR-NAIXUE", "version": 2},
  "catalog_items": [
    {"id": "CI-NAIXUE-WORKDAY-TEA", "version": 1}
  ],
  "claims": [
    {"id": "CL-NAIXUE-SENSORY-REST", "version": 1}
  ],
  "source_batch_ids": ["OB-NAIXUE-0001"],
  "content_hash": "sha256:..."
}
```

Snapshot 不保存“最新”引用，必须固定到具体版本；否则历史 Assessment 无法重放。

## 9. 确定性校验

数据包发布前与浏览器加载时都应检查：

1. ID 唯一且所有引用存在；
2. Catalog Item 的 brand_id 与 Snapshot / Assessment 一致；
3. `eligible` 商品满足 availability、Claim、必填属性和 review gate；
4. `paused / retired / expired / blocked` 商品不能成为新的 `selected`；
5. 选择结果引用的 item 版本必须包含在 Snapshot；
6. Brief 的商品必须来自对应 Assessment 的 `selected`；
7. `needs_evidence` 商品只能进入 `draft_unverified`；
8. Claim 必须适用于该商品、市场和有效期；
9. 修改核心商品字段后，旧 Assessment / Brief 标记 stale；
10. 人工修正追加记录，不覆盖模型原始抽取；
11. 私人来源、签名链接和本地路径不得进入公开数据包；
12. 任何 Agent 输出都不能设置 `automatically_published: true`。

## 10. 品类规则配置

首版用配置而非代码分叉表达品类必填项：

```json
{
  "physical_product": ["market", "availability", "value_proposition"],
  "menu_item": ["market", "availability", "validity_window"],
  "service": ["market", "service_area", "fulfillment_status"],
  "digital_product": ["market", "platform", "subscription_status"],
  "offline_experience": ["market", "venue_or_city", "validity_window"]
}
```

这样既保留统一 Catalog Item，也允许逐步扩展不同商品形态，不需要为每个行业复制一套工作流。

## 11. 前端数据包建议

在现有 `brands.json / trends.json / opportunities.json / briefs.json` 基础上新增：

- `catalog_items.json`
- `claims.json`
- `brand_asset_snapshots.json`
- `onboarding_batches.json`

下一数据版本建议升级为 `0.4.0`，manifest 必须包含新增文件及哈希。前端加载器对 v0.3.0 与 v0.4.0 使用显式版本适配，不在运行时猜字段。
